## 読み方と確かさ

「本人の回想」「当時の会話・作業メモ」「Gitで確認した変更」「Codexでの検証」「今後の計画」を区別する。AIが当時「完成」「原因はこれ」と説明したことだけでは、実機確認や原因特定が済んだとは扱わない。資料の取得状況と出典は[履歴の根拠](history/antigravity-history-evidence.md)に記載する。

日付は日本時間。Gitの日付はコードを登録した日であり、構想・実装・実機書き込みの日と一致するとは限らない。Antigravityの記録は2026年4〜5月の資料が残っている。最初の構想日、最初の実機完成日、すべての版と実機書き込みの対応は未確認。

## 1. 最初にやりたかったこと

2026-10-04の本人の回想では、出発点は**家の温度ログを作り、トレンドグラフで夏にどの程度温度が上がるか見たい**というものだった。初めからAI予測や複数の通信方式を必須としていたわけではない。追加できる機能を知り、興味を持って機能を増やしていった。

この目的を、今後機能を戻す際の基準にする。「家の温度変化を見られるか」「普段の操作を増やしすぎないか」「継続して管理できるか」で必要性を判断する。これは今回の振り返りから定めた基準であり、当時から文書化されていた基準ではない。

## 3. 工夫した点と、確認できる範囲

**本体で変化を読み取れること。** 当時の計画は、最新値だけでなく24時間の履歴を持ち、24/12/6時間の表示切替や値に合わせたグラフの縦軸を用意するものだった。リングバッファで古い値を循環的に置き換える構成を採った。操作や描画を再利用する際は、そのまま正しいと決めず新版で確認する。

**電池と小さな画面の制約への対応。** 旧版はディープスリープ、ボタンによる表示、間引いたグラフ履歴と定期保存を組み合わせた。QRを分割して画面に順番に表示し、ブラウザ側でページを集める方式も試した。これらは当時の工夫であり、今回の常時給電版の必須条件ではない。

**AI予測の試行。** 学習用データの収集、PC/Colabでのモデル生成、model.hを使った本体推論と、Webから外部AIに相談する経路があった。両者は別の機能。会話にはR²=0.995などの出力があるが、学習・評価方法や時系列の独立性を再検証していないため、実運用の予測精度の成果としては使わない。

**壊さずに基準を確認したこと。** Codexでは、実機の読み取りとデータ保全を先に行い、保存ソースのコンパイル結果との差を区別した。実機ログ25,440件はレコード長と計算式を確認し、古いサンプルは8バイト目から読むと全6,346件の式が合うことを確認した。ずれが起きた経路は未特定で、「BLEの欠損が原因」と断定し直していない。

## 4. 困った点と今回の学び

1. **機能を増やした結果、全体を把握しにくくなった。** 本人は興味から追加を重ねたと回想。当時もどのスケッチを使うか、各操作がどう動くかを質問していた。今後は本来の目的に照らして機能を選ぶ。
2. **変更内容を理解しきれないまま反映した。** 本人によれば、英語・コード・GitHubの用語が分からずPRが蓄積し、Julesの提案を十分理解せず取り込んだこともあった。Gitで確認した修正消失の例を添えるが、すべての不具合をJulesに帰属させない。
3. **「修正した」という説明と、実際に直ったことは別だった。** QRの修正報告後にも本人の不具合報告が続いた。新しい版ではコンパイル、実機の操作、送信・通信断・再起動の確認を分けて記録する。
4. **データ・AIの結果を先に信じると判断を誤る。** 当時の会話には、本体は正常な温度なのにWeb集計は異常という報告がある。Codexで元ログと保存サンプルを分けて検査したことで、測定と転送・解析を同じ問題と扱わずに済んだ。

## 5. 機器と選定理由

以下の選定理由は2026-10-04に本人が説明した回想。購入・比較をした日、購入価格、当時比較に使った資料は未確認。「選んだ理由」と「実測で優位性を証明したこと」は区別する。

| 選択 | 資料で確認できる役割 | 本人が重視した理由 |
|---|---|---|
| ESP32C3 | 旧スケッチの対象チップ | 新しさよりネット上の情報の多さを重視し、AIによるコード実装に適すると判断。価格と温度計に必要十分な機能も理由 |
| XIAOの基板 | ESP32C3を小さな基板に載せ、拡張ボードへ接続 | 安さ、必要なピンが多くないこと、省スペースで設置場所を選びやすいこと。対応する拡張ボードの存在も選定理由 |
| Grove AHT20モジュール | 温度・湿度を計測し、I2Cで接続 | 堅牢性・正確性・価格のバランスを期待した。Groveで拡張ボードへ簡単に接続できる安価なモジュールである点も理由 |
| XIAO拡張ボード | OLED、ボタン、ブザー、PCF8563 RTCを利用 | モニター付き、I2CのGrove接続でセンサーを取り付けやすく、XIAOもピンを差し込めること。組み合わせの接続性と動作の確実性を重視 |
| PCF8563 RTC | 時刻保持・表示・記録 | 既存の拡張ボード内の時計を使い、旧版の電池運用・スリープ中の時刻を保持する計画。RTCチップを単体比較して購入したとは確認していない |

全体として、必要な性能・価格・設置しやすさに加え、既製モジュールの組み合わせで接続を簡単にすることを重視している。情報量が他チップより多い、AI実装に常に最適、という一般的なランキングを証明した記録ではなく、本人が当時そう判断した理由として残す。

本人はAHT20の工業用途の実績については記憶が曖昧とした。今回確認した[Seeedの公式説明](https://wiki.seeedstudio.com/ja/Grove-AHT20-I2C-Industrial-Grade-Temperature%26Humidity-Sensor/)は、このGrove製品を産業グレードとして紹介しており、I2CのGrove接続も示している。これは選定理由と整合するが、具体的な工場への導入実績や、本プロジェクトでの校正・耐久試験を確認したという意味ではない。[拡張ボードの公式説明](https://wiki.seeedstudio.com/Seeeduino-XIAO-Expansion-Board/)でもOLEDとGrove接続を確認できる。

今回のWi-Fi版でも既存機器を使う案は、現在の再利用方針として別に記録する。
