## 2026-06-02 - [Canvas Render Overhead in requestAnimationFrame]
**Learning:** In a `requestAnimationFrame` loop, unconditionally assigning `canvas.width` and `canvas.height` forces the browser to reallocate the backing store and reset the 2D context *even if the values haven't changed*. This causes a significant performance bottleneck, especially on mobile devices scanning QR codes. Also, when calculating dimensions based on aspect ratio, the result must be explicitly cast to an integer (e.g., using `Math.floor()`); otherwise, floating-point precision issues can cause the dimensions to always appear "changed" compared to the canvas's internal integer dimensions, leading to continuous resets.
**Action:** When working with Canvas inside rendering loops, always cache the source dimensions (`videoWidth`, `videoHeight`). **Learning:** When using Playwright `page.evaluate()` to benchmark JavaScript or rendering performance, running the code just once or a few times can be misleading due to JIT compilation overhead. Also, when benchmarking DOM elements like Canvas, simply creating them in memory might not trigger realistic browser processing unless they are attached to the DOM (even if hidden with `display: 'none'`).
**Action:** In benchmark scripts, always include a warmup loop (e.g., running the target code ~100 times before starting the timer) to stabilize JIT optimization. Additionally, when testing DOM elements, append them to `document.body` (with `style.display = 'none'` if visual output isn't needed) to ensure the browser processes them correctly.
